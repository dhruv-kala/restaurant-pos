# Task 28.3 - Feature Entitlements

## Status

Complete.

## Objective

Control tenant feature availability through one authoritative entitlement
evaluation boundary.

## Implemented Scope

- Tenant-scoped `TenantEntitlement` overrides
- Exact subscribed plan-version features as the entitlement baseline
- Active override precedence over plan features
- Fail-closed evaluation when no eligible subscription exists
- Effective date windows and explicit override revocation
- Tenant-scoped idempotency and optimistic concurrency
- Reusable `@RequiresEntitlement()` decorator and `EntitlementGuard`
- Platform administration and tenant-admin self-read APIs
- Audit events for create, update, and revoke operations

Example feature keys include `inventory`, `communication`, `loyalty`,
`customer-app`, and `api`.

## Evaluation Rules

1. `SUPER_ADMIN` actors may bypass business feature gates for platform support.
2. A tenant must have a current, in-period `ACTIVE` or `TRIAL` subscription.
3. An active tenant override takes precedence over the subscribed plan feature.
4. Without an active override, the exact plan-version feature is used.
5. Missing features and ineligible subscriptions are disabled.

Suspended, expired, cancelled, future, and ended subscriptions cannot grant
feature access. An override cannot bypass subscription eligibility.

## Enforcement Contract

Business routes that become subscription-controlled must apply both
`JwtAuthGuard` and `EntitlementGuard`, then declare their feature key with
`@RequiresEntitlement('<feature-key>')`.

Existing business modules were not enabled en masse in this task because
existing tenants have not yet been migrated onto subscription records. Feature
gates must be introduced deliberately with subscription rollout data so
production tenants are not unintentionally locked out.
