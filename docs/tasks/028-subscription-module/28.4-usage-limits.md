# Task 28.4 - Usage Limits

## Status

Complete.

## Objective

Enforce tenant subscription usage limits through one centralized, atomic
service.

## Implemented Scope

- Tenant-scoped `UsageCounter` current-period projections
- Immutable `UsageCounterEvent` operation history
- `LIFETIME`, `DAILY`, and `MONTHLY` UTC periods
- `BLOCK`, `WARN`, and `ALLOW` over-limit policies
- Atomic, advisory-locked consumption
- Tenant-scoped idempotency and request fingerprints
- BigInt-safe API response values
- Platform reconciliation with optimistic versions
- Tenant-admin self-read APIs
- Audited denied, allowed-overage, and reconciliation operations

Examples include outlet count, user count, API requests, and storage
allocation.

## Entitlement Metadata

Task 28.4 reads optional metadata from the effective Task 28.3 entitlement:

```json
{
  "usagePeriod": "MONTHLY",
  "overLimitAction": "BLOCK"
}
```

Defaults:

- `usagePeriod`: `LIFETIME`
- `overLimitAction`: `BLOCK`

The effective entitlement `limitValue` is the usage ceiling. A null
`limitValue` means unlimited usage while the feature remains enabled.

## Enforcement Contract

Business services call `UsageLimitsService.consumeForActor()` before committing
a metered action. The call:

1. Resolves the actor's trusted tenant.
2. Evaluates the current entitlement.
3. Resolves the UTC usage period.
4. Locks the tenant/feature/period counter.
5. Replays or records the idempotent operation.
6. Applies the configured over-limit policy.

`BLOCK` denies consumption beyond the limit. `WARN` and `ALLOW` permit the
operation and return an over-limit result.

Existing business modules were not mass-integrated because existing tenants
have not yet been migrated onto subscription records. Each business integration
must use the centralized service during deliberate subscription rollout.
