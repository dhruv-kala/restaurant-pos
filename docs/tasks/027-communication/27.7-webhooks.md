# Task 27.7 — Webhooks and Delivery Tracking

## Status

Complete.

## Objective

Implement provider webhook processing and centralized delivery status synchronization.

## Scope

Implement:

* CommunicationWebhook
* webhook ingestion
* webhook verification
* delivery status updates
* bounce handling
* complaint handling

Do not implement:

* marketing automation
* campaign tracking
* advanced analytics

## Ownership

* webhook processing
* delivery status synchronization
* provider event history
* webhook verification

## Data Model

* CommunicationWebhook

## Supported Events

Email:

* delivered
* bounced
* complaint

SMS:

* delivered
* failed

WhatsApp:

* delivered
* read
* failed

Push:

* delivered
* failed

## Invariants

* All webhooks must be verified.
* Invalid signatures are rejected.
* Webhook events are immutable.
* Webhook processing is idempotent.
* Duplicate events do not create duplicate updates.
* Tenant isolation is enforced.

## API

Provider Webhooks:

* POST /communication/webhooks/:provider

Administrative:

* GET /communication/messages/:id/attempts

## Completion Criteria

* Webhooks are verified.
* Delivery statuses update correctly.
* Duplicate processing prevented.
* Audit events generated.
* Build passes.

## Implemented

* Immutable, tenant-scoped `CommunicationWebhook` event history with forced RLS
* Twilio request-signature verification using the official SDK
* Provider-neutral HMAC-SHA256 verification for future email and push adapters
* Idempotent provider-event ingestion with transaction advisory locking
* Sanitized and bounded webhook metadata without raw payload retention
* Centralized monotonic attempt and message delivery-state synchronization
* Email delivered, bounced, and complaint state handling
* SMS delivered and failed state handling
* WhatsApp delivered, read, and failed state handling
* Generic push delivered and failed state contracts
* Verification-failure and processing audit events
* Protected `GET /communication/messages/:id/attempts`

SMTP and FCM do not expose a universal callback contract. Their future provider
adapters can use the signed provider-neutral webhook envelope without changing
the persistence or delivery-state services.
